目标环境：`myrepo-d7go4fyg918beac63`，现有 CloudBase MySQL。此文件是待审查的计划，**尚未执行**；实际 SQL 见 [phase12-draft.sql](../database/mysql/phase12-draft.sql)。当前因下述账号标识比较问题暂停执行，须先确定安全方案并重新验证。

1. 在现有 `users` 表的 `(openid, status)` 上新增唯一索引，供两个新表的复合外键引用；不修改现有行。建索引可能短暂影响数据库操作。
2. 新建 `ai_daily_quota`，记录每个账号的每日调用次数，用于服务器端限流。

两个表都关联现有账号：账号进入删除状态时授权记录随状态冻结；注销过程清除该账号的 AI 记录。旧的设备、维护、保修、附件、提醒和协议记录不改动。删除旧表、清空数据和迁移环境不在计划内。

执行前确认本人可用的备份、实时表结构、索引和表名；逐条执行，任一步失败即停止，先检查实际状态，不能直接重复非幂等的 `ALTER TABLE`。拟先按 [identity-collation-draft.sql](../database/mysql/identity-collation-draft.sql) 修改九张现有表的 `openid` 排序规则为 `utf8mb4_0900_bin`，随后新表的 `openid` 采用相同规则；九张表的修改超出先前针对索引及新表的授权，不能直接执行。MySQL 的多条 DDL 各自提交，需先确定如何阻止迁移期间的业务写入和定时器执行、失败后怎样安全恢复，并通过隔离 MySQL 和 CloudBase 权限验证。建表后核对外键和访问权限，再用隔离测试验证云端 SDK 的条件更新及账号隔离；不拿真实账号做注销测试。未配置密钥和部署 AI 函数前，新表不会启用 AI。线上业务函数依赖两表，不能在迁移前部署新版业务函数。

本地 MySQL 8 的无网络容器已使用真实建表脚本和虚构数据验证排序规则迁移：原记录保留、仅大小写不同的两个账号相互隔离，AI 外键及注销冻结正常；测试容器和匿名卷已清除。测试可用 `node scripts/phase12-mysql-isolation.mjs` 重现，依赖本地已有 MySQL 8 Docker 镜像。尚未验证 CloudBase MySQL 的生产权限和 SDK；开发者工具的身份探针已验证，iPhone 和微信原生定时器仍须验证。若发布出现问题，应先停止 AI 入口并保留表与业务数据排查；任何删除表或回滚数据的操作需要另行评估。

只读检查发现现有业务表 `openid` 使用不区分大小写的排序规则；线上只读的虚构字符串比较已确认不同大小写会被视为相等。这可能影响不同标识的隔离，不能把现有排序规则视为字节级身份校验。本地入口增加了账号标识精确匹配及未注册账号拦截，但这不保证历史业务表中的每条记录都按精确标识过滤。2026-11-10 只返回布尔值的线上检查显示，八张关联表没有发现与所属用户仅大小写不一致的记录，也没有发现找不到用户的记录；这只代表查询时的数据状态，执行前需重新检查，不能证明历史上没有问题。九张表的 `openid` 均为非空 `varchar(128)`；只读元数据没有发现引用这些列的外键，变更前仍需复核。

本人已允许原先新增两张 AI 表和索引；由于发现新问题，上述九张已有业务表的排序规则修改不在该授权之内。须先完成迁移期间写入冻结和失败恢复方案，再向本人明确展示新增影响并取得单独授权。
